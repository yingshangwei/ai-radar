# 动态关联发现与潜力预判

服务端在正式采集入库时、社交互动门槛之前保存近期 AI 候选。新 `discover` 独立队列执行一次结构化模型判断，后台自动继续；App 不需要保持打开或逐条点采集。

## 两条发现路径

- 已关注来源或综合互动达到 100 的发言，检查原文明确关联的用户、团队、公司。X 使用官方 `entities.mentions.username`、直接回复和引用作者的展开资料，保存真实用户 ID、账号名、简介和证据。仅名字相似、资料缺失、模型猜测的账号不会加入关注。
- 未关注且互动低于原有门槛的内容，有足够正文、研究或发布信号时仍可成为候选。模型判断 AI 相关性、新颖性、具体程度、潜在影响和判断把握；新颖性和影响至少 75、具体程度至少 60、把握至少 75，且给出原文逐字证据后才可入选。数值是筛选评分，不是未来走红概率。
- 入选内容以「前瞻 / 潜力预判」进入原雷达，保留原作者、发表时间、原文和真实互动数；理由、不确定点独立展示。文章中文、AI 标题、直接来源解读仍由既有服务端翻译和审核流程生成，不由发现模型改写文章。
- 后续正常采集再次遇到相同发言时更新真实互动，指标变化不重复翻译或判断。综合互动达到至少 30 且为初次的三倍时，显示实际「已升温」。这只是后续采集观察，不承诺逐帖定时复查或必然走红。低热内容后来成为热门种子时，可零模型应用已保存的关联建议。

只处理源明确提供的一层关联；不递归追踪他人的关注列表、引用链或外部链接。现有 X 采集的覆盖范围、请求数和分页状态仍是实际覆盖边界。

## 自动试关注与用户控制

关注建议需要真实身份资料、原文关联证据、明确 should_watch 和至少 85 的判断评分。默认每天最多新增 2 个、同时最多 6 个，7 天后自动到期停止；App 可关闭，也可主动保留。这里操作的是 Radar 服务端关注名单，不会替用户在 X 社交账号点关注。

用户已有关注不被接管，已关闭账号不会自动恢复。用户操作自动关注的开关后，该条由用户管理，不再自动过期。发现真实 ID 改名或同名账号身份冲突时暂停自动管理的旧关注，保留历史供核对；不会把账号所属公司凭空填写。只有名称、没有已核验账号的团队/公司保存为身份待确认，查询接口可查看理由和来源。

## 预算、替换与恢复

```toml
[discovery]
enabled = true
max_candidates_per_day = 60
max_calls_per_day = 20
max_calls_per_candidate = 2
batch_size = 4
session_reuse = true
session_directory = "/var/lib/ai-radar/agent-sessions"
session_max_turns = 32
session_max_age_hours = 168
max_auto_watches = 6
max_new_watches_per_day = 2
trial_days = 7
```

候选默认只取最近 48 小时，未完成队列上限 120。每日 60 个候选和 20 个候选判断额度各半分给低热度与热门/已关注来源；奇数额外一个给低热度，两个池互不挤占。同一发言始终保留首次归类，指标变化、改正文和跨天不能重置其既有调用记录。每日额度按 UTC 日期统计，每个候选最多两次逻辑调用。Codex 会话模式每次任务最多处理 4 个候选，组成一次真实批量调用；4 个候选仍消耗 4 个原有判断额度，不扩大每日模型预算。其他提供方保留原每任务最多两条的调用方式。

默认复用 `[provider]` 的 Codex 授权，可通过 `[discovery.provider]` 替换为既有支持的模型 API、Claude CLI 或其他命令适配器，无新增采集依赖。逻辑调用不等同底层请求次数：API SDK 可能进行其有限重试，CLI 内部请求数不可由 Radar 精确计量。

每次调用先在 SQLite 持久预约、记录 owner、租约、证据指纹和提供方标识，结果成功后保存回执再应用。应用异常只重试保存结果的应用步骤。明确的 429/5xx 最多重试一次、等待 15 分钟；超时、进程中断、CLI 非零退出等结果不明确的情况标记 unknown，自动重启不会重投。格式或证据不合格、余额不足、授权失败进入待处理状态，不把失败变成通过。读取 API 不触发模型。

## Codex 会话与批次

`session_reuse=true` 且实际发现提供方为 `codex` 时，前瞻预判和关联实体识别共用专属 `discovery` 会话。第一次使用 `codex exec --json`，后续批次通过 `codex exec resume <明确保存的会话 ID>` 继续；不使用 `--last`。摘要生成、事实审核、翻译仍保留各自的调用与审核隔离，不与发现会话混用。更换为 API 或其他 CLI 后仍使用已有通用 Provider 接口，不要求它们支持 Codex 会话。

默认 32 批或 7 天后，在下一批之前换新会话。提供方配置、模型、发现策略、输出结构或提示规则改变也会换新；未知结果、格式失败或损坏会话关闭后，其他候选可以继续进入新会话。换会话不清空候选调用记录、限额或待处理问题。旧会话和批次回执保留供排查。

队列按候选入库时间排序，每个批次先原子保存成员、冻结原文、调用额度、提示和请求指纹。SQLite 数据库旁的独占文件锁覆盖完整 CLI 生命周期，并传给子进程；第二个执行器拿不到锁时继续排队，不能因租约超时抢占仍存活的 CLI。服务端必须使用同一数据库文件和其本地锁文件，不能把同一数据库复制成两个并行生产实例。

CLI 的逐行事件、会话 ID、退出码和结果存入权限为 0700/0600 的批次目录。服务重启或维护时，先核对完整 `turn.completed`、退出码 0、请求指纹、精确批次 ID 与全部候选 ID，然后恢复已完成结果，不再次调用模型。证据必须逐字属于对应候选；缺项、重复项、历史候选或跨候选引用让整批进入待处理，不能把未返回的项留在 pending 或发布部分错误结果。只有通过全部校验的判断才能进入既有自动发布流程。

没有可证明完成的回执时，该批进入 `unknown` 并关闭会话，保留调用额度与证据，不盲目重发。其他候选照常处理。普通候选到期会由周期维护显式标记 `expired`，不必等待新文章触发收尾；已完成判断的应用失败按原 15 分钟退避重试落库步骤。发现任务执行器发生异常后也会在 15 分钟后重新检查队列；恢复入口先核对批次账本，不重放未知调用。

新增 `agent_sessions`、`agent_batches` 两张状态表。`GET /v1/status` 的 `discovery.sessions` 提供批次完成/未知数量、当前会话及已用批次数、每日实际批次数、最早等待时间；`calls_today` 仍按候选判断计数。App 0.9 可继续使用，现有任务/发现错误状态仍可查看。本次服务端更新无需安装新包。

官方会话与事件协议：[Codex 非交互运行](https://learn.chatgpt.com/docs/non-interactive-mode)。服务器 CLI 的实际 `exec` 与 `exec resume --help` 同时作为参数兼容性检查依据。

新增四张私有状态表：`discovery_candidates`、`discovery_calls`、`discovery_entities`、`discovery_watches`；不修改已有文章、翻译与审核数据结构。

接口：现有 `/v1/status` 增加发现状态；`/v1/articles` 和详情增加可选 discovery；`/v1/watches` 增加可选试关注信息；认证后的 `GET /v1/discovery/entities?limit=50` 提供关联依据；管理员正式任务支持 `kind=discover`。无需手工触发，正式采集后自动入队。

官方字段依据：[X Expansions](https://docs.x.com/x-api/fundamentals/expansions)、[X Fields](https://docs.x.com/x-api/fundamentals/fields)、[Recent Search](https://docs.x.com/x-api/posts/search-recent-posts)。使用展开资料减少额外逐账号请求，但用户资源计费仍以 X 的实际规则为准。
