# 后台任务与恢复

API 使用 SQLite 持久队列，不再用内存 task + 一把全局锁表示全部工作。采集、翻译、网页/日报处理有独立执行通道；同类型重复请求合并为一个后续待办。网页和日报通道在已完成批次之间轮转。

- `queued` 表示已持久保存的待办，`running` 才是取得执行权的任务。
- 每 15 秒更新工作进程心跳；只有进入新阶段才更新进展时间，心跳不等于翻译已完成。
- 每 60 秒检查可执行积压和丢失的执行协程。翻译每批最多 2 份缓存、每份最多 2 个逻辑模型阶段；网页每批处理 1 个来源和 1 个消息标题。仅在模型结果已保存的边界主动让出，剩余工作 30 秒后续跑。
- 已知连接失败最多执行 3 次，间隔 60 秒、300 秒；内容层保留各自已有的调用次数与退避。日报仍使用每个统计窗口总计 3 次的原有预算。
- 服务退出将未完成任务意图保存回队列；启动时仅在原执行进程已退出的证据下接续。重启不消耗已知网络失败的剩余次数。数据库旁的 `.jobs.lock` 防止多个 API 执行器同时接管。
- 翻译和摘要复用原有阶段记录。结果未知的模型调用、未通过的相同候选不会自动重投。此类条目显示需要处理；它们不是正常的等待队列。旧调用租约尚未过期时仍保留保护，后续资格扫描在到期后恢复允许执行的阶段。

手机端“你的雷达”显示各任务的入队、开始、阶段、心跳及重试时间；中文阅读区区分处理中、待处理、重试与需要检查。断网时明确显示上次状态。余额不足继续使用已有的翻译供应商余额提醒。

## 首次从旧版迁移

旧版把排队中的任务也记录为 `running`，且没有执行者、请求日期或心跳，不能仅凭时间推断已中断。部署必须先验证旧 API 进程退出，再持有 `.jobs.lock` 调用 `JobSupervisor.recover_interrupted(recover_legacy=True)`；这个同步入口只迁移任务意图，不启动执行器或调用模型。

同类型采集/翻译/网页旧任务合并，原任务记录保留；缺失请求日期的旧日报保持需要处理，不猜测日期重放。升级仅为 `jobs` 增加控制列。原文、译文、候选和审核记录不做人工编辑。

## 验证

自动化回归包含旧表迁移、11 个旧任务合并、重复提交、有限重试、取消/重启、进程锁、三个通道并行、跨进程翻译续跑、已知否决不重复审核、未知请求不重投及只读 API。实际部署状态和安装包见发布记录。
